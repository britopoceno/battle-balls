## Story

**Como** desenvolvedor executando o passo 4 do plano de construção da Fase 3 (`docs/architecture-e3.md`
§12),
**eu quero** implementar o fluxo completo de telas do cliente — draft, builds (com timer), rodada (canvas),
placar/loja — espelhando `FaseDaPartida` de `match/`, trocando o driver `dummy` pelo `heuristic` real e
filtrando `minhasBolas` pelo lado do jogador (que agora alterna a cada rodada, R-06),
**para que** exista, pela primeira vez, uma partida jogável do início ao fim contra o bot real — o cliente
que os portões P3.1 a P3.4 vão medir com humano no controle.

## Depende de

`e3.1` (`src/shop/` — catálogo e preview de stat efetivo), `e3.2` (`src/match/` — `EstadoPartida`,
`visaoPara`, redutor `aplicar`) e `e3.3` (`src/bot/partida.ts` — política de partida do bot). O cliente
precisa das três: da loja para desenhar preço/catálogo, de `match/` para orquestrar o fluxo de fases, e do
bot de partida para ter um oponente que joga a partida inteira, não só a rodada.

## Acceptance Criteria

**Verificação de compatibilidade (herdada, todas as stories):**

1. `npm run check` verde.
2. `npm run sim:check` verde, com **golden hash idêntico** ao baseline nas seeds 1, 2, 3, 7, 11.
   `sim:check` **não vê o cliente** — este AC prova que o motor não regrediu, não que o cliente funciona; a
   prova do cliente é o AC 3.

**Smoke visual — a prova que `sim:check` não dá (§12, passo 4; Anexo B, P3.4):**

3. **Smoke visual (P3.4):** uma partida completa jogada manualmente **no dispositivo — celular real**, do
   draft ao fim, **sem erro de console**. O padrão é o de P1.2, e P1.2 enumera as superfícies exercitadas
   (`docs/prd.md` §2, E1: *"Smoke visual próprio no dispositivo — seleção de build, arena, física, HUD,
   cooldown, arrasto nas duas mãos, fim de rodada, sem erro de console"*); `docs/prd.md` §2, E3 define P3.4
   como *"Smoke visual no dispositivo, **como em P1.2**"*. Seguindo esse padrão, a execução precisa
   exercitar, na mesma sessão, cada superfície **nova** desta fase:

   | # | Superfície a exercitar na sessão | Por que ela precisa estar na lista |
   |---|---|---|
   | a | tela de **draft** → escolha registrada | primeira tela do jogo; nunca existiu antes |
   | b | tela de **builds** com escolha manual, **e** um estouro de timer de 30s produzindo `buildPadrao` | o caminho do timeout (D-06) só existe aqui; é o único jeito de ver que `match/` recebe a decisão |
   | c | **rodada** no canvas, com arrasto nas duas mãos (herdado de P1.2) | é a superfície que P1.2 já cobria e que não pode ter regredido |
   | d | **placar** e **loja**: ao menos uma **compra** concluída e o **valor efetivo** exibido (AC 6) | é a decisão econômica, o motivo da fase existir |
   | e | ao menos uma rodada jogada **do lado 1** (alternância de R-06, AC 13) | input e HUD invertidos é o modo de falha mais provável desta story |
   | f | **fim de partida** (Bo5 resolvido, não abandonado no meio) | o fim de rodada era estado morto antes (AC 11) |

   Ausência de erro de console é **necessária e não suficiente**: uma superfície da tabela que não foi
   aberta na sessão não conta como coberta. Navegador desktop serve para desenvolvimento e depuração, mas
   **não substitui** a execução no celular — foi exatamente essa a lição de P1.2 (`docs/prd.md`: *"P1.2 não
   é redundante com `npm run sim:check`"*), e a Seção Testing desta story já exigia celular.

**Máquina de estados da UI (§11.1):**

4. O fluxo de tela segue exatamente:
   ```
   draft ──▶ builds ──▶ rodada ──▶ [placar] ──▶ loja ──▶ builds? ──▶ rodada ... ──▶ fim
   ```
   `FaseDaPartida` (de `match/types.ts`, `e3.2`) é a **fonte** — a UI não tem estado de fase próprio, só
   desenha o que a fase diz. Isso evita a classe de bug "a tela acha que está na loja e a partida acha que
   está na rodada".
5. Tabela de telas, superfície e I/O (§11.1):

   | Tela | Superfície | Lê | Escreve |
   |---|---|---|---|
   | Draft | DOM (overlay) | `visaoPara(e, humano).draft` | `{t:'draft'}` |
   | Builds | DOM — reaproveita os cards de `montarSeletor` que já existem (`main.ts:153-181`) | `visaoPara(...).eu.personagens` | `{t:'build'}`, `{t:'pronto'}`, timeout → `{t:'buildPadrao'}` |
   | Rodada | canvas — o laço de hoje, sem mudança estrutural | `World` | `Command[]` |
   | Placar / loja | DOM (overlay) | `visaoPara(...)`, catálogo, preços efetivos | `{t:'compra'}`, `{t:'trocaDeBuild'}`, `{t:'pronto'}` |

**Preview de valor efetivo — nunca reimplementar a fórmula (§7.3, §13.3):**

6. A tela de loja mostra o **valor efetivo** do item (não o valor nominal), calculado chamando
   `recomputeStats` sobre uma bola sintética — usando o **helper único** extraído em `e3.1`. **Nunca**
   reimplementar a fórmula de stats no cliente — isso criaria uma terceira fonte de verdade.

**Mudanças em `main.ts` (§11.2):**

7. `world` deixa de ser variável global de módulo e passa a ser criado por
   `setupDaRodada(estadoPartida)` (de `match/`, `e3.2`).
8. `meuTime` (`main.ts:28`) **some**: a composição vem do draft, e o lado vem de `ladoDoJogador`
   (`ResultadoRodada.ladoDoJogador`, `e3.2`/§5.3).
9. `minhasBolas()` passa a filtrar por `meuLado`, **não** por `team === 0` — literal:
   `balls.filter(b => b.team === meuLado)`.
10. `dummyCommands` é substituído por `botCommands` + `createBot(seedDaRodada, ladoDoBot)`, **recriado a
    cada rodada** (invariante M-1, `e3.2`).
11. O fim da rodada deixa de ser um estado morto (`world.over` e nada acontece): passa a emitir
    `registrarRodada(...)` (de `match/`).
12. `INPUT_DELAY_TICKS = 0` **continua 0** — é desvio consciente já registrado na arquitetura; P4.1 é da
    Fase 4. Não mexer nisso nesta story.

**Alternância de lado (§5.3, R-06 opção b aprovada):**

13. O cliente sabe renderizar e comandar o time 1 — o layout já é simétrico (`layout.ts`), então nenhuma
    mudança estrutural de layout é esperada, só a leitura correta de `meuLado` por rodada.

**Compras não são secretas (§4.1, nota explícita):**

14. `PersonagemVisivel.itens` é visível nas duas variantes do tipo de `visaoPara` — a tela de loja/placar
    **não** deve esconder os itens comprados pelo oponente. RF-04 declara segredo só para a *seleção de
    build*.

**`render.ts` (§11.2):**

15. `render.ts` não muda estruturalmente, exceto o HUD do placar (`desenharHud` já existe e deve ser
    conectado ao placar real) e o fato de que o time do humano pode ser 1.

**Draft com composição fixa (herdado de `e3.2`, R-01 opção B):**

16. A tela de draft existe e é funcional (lê `pool`/`ordem`, escreve `{t:'draft'}`), mas a composição
    exercitada é fixa `[golem, vex]` para os dois jogadores — não implementar escolha de personagem com
    efeito real no resultado; a estrutura é genérica, o conteúdo é fixo nesta fase (R-01).

## Dev Notes

### A máquina de estados (fonte: `docs/architecture-e3.md` §11.1)

```
draft ──▶ builds ──▶ rodada ──▶ [placar] ──▶ loja ──▶ builds? ──▶ rodada ... ──▶ fim
  │         │           │                      │
  DOM       DOM       canvas                  DOM
```

> `FaseDaPartida` (§2.3) é a fonte; a UI não tem estado de fase próprio, só desenha o que a fase diz. Isso
> mata a classe inteira de bug "a tela acha que está na loja e a partida acha que está na rodada".

> **Por que DOM para as telas e canvas para a rodada:** o overlay, os cards e o CSS já existem e já foram
> validados em celular real na Fase 1 (P1.1/P1.2). Recriar isso em canvas seria trabalho novo para um
> resultado pior em acessibilidade e em rolagem — e a rodada continua sendo canvas porque é onde há 60Hz.

[Fonte: `docs/architecture-e3.md` §11.1]

### O que muda em `main.ts` (fonte: §11.2, literal)

> Hoje ele é um laço de rodada única com um seletor de build de bancada. Depois:
> - `world` deixa de ser variável global de módulo e passa a ser criado por `setupDaRodada(estadoPartida)`;
> - `meuTime` (`main.ts:28`) some: a composição vem do draft, e o lado vem de `ladoDoJogador` (§5.3);
> - `minhasBolas()` passa a filtrar por `meuLado`, não por `team === 0`;
> - `dummyCommands` → `botCommands` + `createBot(seedDaRodada, ladoDoBot)`, recriado por rodada (M-1);
> - o fim da rodada deixa de ser um estado morto (`world.over` e nada acontece) e emite
>   `registrarRodada(...)`;
> - `INPUT_DELAY_TICKS = 0` continua 0 — é desvio consciente registrado, e P4.1 é da Fase 4.
>
> Nada disso muda `render.ts` estruturalmente, exceto o HUD do placar (`desenharHud` já existe) e o fato de
> que o time do humano pode ser 1.

[Fonte: `docs/architecture-e3.md` §11.2]

### O preview de stat da loja — a quase-terceira fonte de verdade (fonte: §7.3, §13.3)

> Se um jogador comprar dois itens do mesmo campo e o teto morder, ele **paga por um bônus que não
> recebe**. A tela da loja precisa mostrar o valor **efetivo**, e o único jeito honesto de calculá-lo é
> chamar `recomputeStats` sobre uma bola sintética — **nunca** reimplementar a fórmula no cliente.

[Fonte: `docs/architecture-e3.md` §7.3 — o helper em si já foi extraído em `e3.1`; esta story só o
**consome** na tela de loja.]

### Compras não são secretas (fonte: §4.1)

> Nota registrada, porque o texto aprovado não fala disso: as compras não são secretas. RF-04 declara
> segredo para a *seleção de build* e mais nada; esconder também a loja seria regra que ninguém escreveu
> (Artigo IV). `PersonagemVisivel.itens` é visível nas duas variantes do tipo.

[Fonte: `docs/architecture-e3.md` §4.1]

### Relógio de parede — onde ele mora (fonte: §2.6)

> RF-04 pede um timer de 30 segundos. [...] `match/` só conhece decisões explícitas. O cliente é dono do
> relógio e, quando ele estoura, **emite uma decisão** (`{ t: 'buildPadrao' }`).

[Fonte: `docs/architecture-e3.md` §2.6 — o timer em si é responsabilidade desta story (cliente); `match/`
(`e3.2`) só sabe reagir à decisão que o timeout produz.]

### Pixel/cor/layout não são desta story (fonte: §11, preâmbulo)

> Arquitetura de dados e de fluxo. Pixel, cor e ergonomia são @ux-design-expert e não estão aqui.

[Fonte: `docs/architecture-e3.md` §11] — esta story implementa a estrutura funcional das telas reaproveitando
o que já existe (`montarSeletor`, overlay, CSS de P1.1/P1.2); refinamento visual fino não é bloqueante para
o smoke visual do AC 3, que exige apenas ausência de erro de console numa partida jogável.

### O que esta story explicitamente NÃO faz

- Não implementa a política de compra/draft/build do bot — isso é `e3.3` (consumida aqui, não criada aqui).
- Não implementa o coletor de telemetria — isso é `e3.5` (mas os eventos que `aplicar` emite, de `e3.2`, já
  existem; o cliente não precisa fazer nada especial para "gerar" eventos, eles nascem do redutor).
- Não corrige a fórmula de resolução de dano nem qualquer coisa de `sim/` — nenhuma linha de `sim/` deve ser
  tocada.
- Não decide números finais de D-09 — usa o que `e3.2` já definiu como provisório.
- Não refina pixel/cor/ergonomia além do necessário para reaproveitar os componentes existentes.

### Testing

- Rodar `npm run sim:check` e confirmar golden hash idêntico — o cliente não deve ter regredido o motor.
- Rodar `npm run check` e confirmar 0 erros de `tsc`.
- **Smoke visual (P3.4, obrigatório, não substituível por teste automatizado):** jogar uma partida completa
  no dispositivo real (celular, seguindo o precedente de P1.1/P1.2 da Fase 1) do draft ao fim, sem erro de
  console. `sim:check` não cobre o cliente — esta é a única prova que cobre.
- Teste manual dirigido: confirmar que, numa rodada em que o humano é o time 1 (após alternância), o input

- Teste manual dirigido: na tela de loja, comprar um item que estoura o teto de um campo e confirmar que o
  valor efetivo exibido reflete o clamp (não o valor nominal).
