## Acceptance Criteria

**Invariante de projeto (§2.1) — base de tudo o mais:**

1. O bot emite **`Command[]` e nada mais** — `{tick, ballId, slot: 'ability'|'ult', dx, dy, mag}`. Ele não
   move a bola (RF-12: IA de movimento é autoral do personagem), não dispara o ataque básico (RF-13:
   automático), não escolhe build, não compra item, não drafta.

**Assinatura e estado (§2.7):**

2. `src/bot/heuristic.ts` (novo) exporta:
   ```ts
   export const BOT_VERSION = 'heuristic-1'
   export interface BotConfig { /* os campos de PRESET_ARNES */ }
   export const PRESET_ARNES: Readonly<BotConfig>
   export interface BotState {
     readonly team: Team
     readonly cfg: Readonly<BotConfig>
     rand: () => number
     porBola: Record<number, EstadoBola>
   }
   export function createBot(matchSeed: number, team: Team, cfg?: Readonly<BotConfig>): BotState
   export function botCommands(view: WorldView, bot: BotState): Command[]
   ```
3. O bot joga os dois lados com o **mesmo código**, parametrizado só por `team` — não existe ramo por
   `team` em nenhum ponto do algoritmo além de exatamente dois pontos: quais bolas são "minhas" e qual
   stream de PRNG é meu (RF-45).

**Chance de acerto (§2.3) — um estimador, cinco formas, zero ramos por personagem:**

4. Para uma bola `self`, um inimigo `e` vivo e a forma `S` do slot avaliado, a chance de acerto é calculada
   exatamente pela fórmula (ver Dev Notes para o pseudocódigo completo):
   `pAcerto = raioEf² / (raioEf² + sigma²)`, com `sigma` incorporando a previsão de 1ª ordem do movimento do
   alvo, o próprio jitter do bot, e o erro de alcance — nenhum ramo condicional por `charId`.
5. `raioEf` e `tImpacto` são derivados do `kind` de `AimSpec` (`burst`/`raio`/`dash`/`reposicao`/`utilidade`)
   sem nenhum `if (charId === ...)`.

**Valor esperado (§2.4):**

6. `VE(mira) = Σ pAcerto(e|mira) * peso(e)` somado sobre **todos** os inimigos vivos (não só o alvo
   pretendido), com `peso(e) = 1 + PESO_FERIDO * (1 - e.hp/e.stat.maxHp)`.
7. O dano da habilidade **não** entra em `VE` — o bot não sabe quanto a habilidade machuca (evita a segunda
   fonte de verdade de que `AimSpec` já se protege, §2.2). Consequência aceita: o bot escolhe *quando* e
   *onde*, não *qual* habilidade (cada bola só tem uma ativa, RF-03).
8. Slots `reposicao` e `utilidade` não têm `VE` e seguem política própria e declarada: `reposicao` foge
   (mira na direção oposta ao inimigo mais próximo) se `hp/maxHp < FUGA`, senão mira no inimigo mais
   próximo se ele estiver além do alcance do ataque básico, senão não casta; `utilidade` casta se
   disponível e o inimigo mais próximo estiver dentro de `[minRange, maxRange]`, mirando nele.

**Limiar com decaimento (§2.5):**

9. `casta se VE_melhor ≥ limiarEf(slot)`, onde
   `limiarEf(slot) = LIMIAR[slot] * max(PISO_LIMIAR, 1 - esperaMs/DECAIMENTO_MS)` e `esperaMs` é o tempo
   desde que o slot ficou disponível — implementado exatamente assim, para que um personagem cujo `VE`
   raramente cruza o limiar não fique com o recurso permanentemente parado.

**Jitter (§2.6) — três fontes, todas do stream do bot:**

10. Jitter de ângulo: rotaciona `(dx,dy)` por `(r()*2-1) * JITTER_RAD`.
11. Jitter de distância: `mag += (r()*2-1) * JITTER_MAG`, clampado em `[0,1]`.
12. Jitter de reação: o próximo instante de decisão da bola é
    `tick + REACAO_TICKS + floor(r() * REACAO_JITTER_TICKS)`.

**`PRESET_ARNES` — valores exatos (§2.6):**

13. `PRESET_ARNES` é `Readonly` e contém exatamente:
    `LIMIAR.ability = 0.55`, `LIMIAR.ult = 0.80`, `PISO_LIMIAR = 0.35`, `DECAIMENTO_MS = 8000`,
    `PESO_FERIDO = 1.0`, `FUGA = 0.35`, `LAG_S = 0.08`, `JITTER_RAD = 0.12`, `JITTER_MAG = 0.10`,
    `REACAO_TICKS = 9`, `REACAO_JITTER_TICKS = 7` — política congelada, idêntica para os dois times

### §2.3 — chance de acerto (pseudocódigo completo)

```
d          = dist(self, e)                        // superfície a superfície não; centro a centro
tImpacto   = S.kind === 'burst' ? S.delayMs/1000
           : S.kind === 'raio'  ? d / S.speed
           : S.kind === 'dash'  ? d / S.speed
           : 0
alvoPrev   = { x: e.x + e.vx*tImpacto, y: e.y + e.vy*tImpacto }   // liderança de 1ª ordem
dPrev      = dist(self, alvoPrev)
alcanceEf  = clamp(dPrev, slot.minRange, slot.maxRange)
erroAlcance= |dPrev − alcanceEf|                  // o que a habilidade não alcança vira erro, não corte

raioEf     = S.kind === 'burst' ? S.radius
           : S.kind === 'raio'  ? S.radius + e.stat.radius
           : /* dash */           self.stat.radius + e.stat.radius

sigma      = |v_e| * (tImpacto + LAG_S)           // o alvo muda de ideia depois que eu miro
           + JITTER_RAD * dPrev                    // o bot sabe que ele mesmo treme (§2.6)
           + erroAlcance

pAcerto    = raioEf² / (raioEf² + sigma²)          // ∈ (0,1], 1 quando sigma → 0
```

Motivo de cada escolha (não implementar diferente sem entender o porquê):

- `raioEf²/(raioEf²+sigma²)` em vez de corte duro: contínuo, gradiente para "qual alvo tem mais chance".
- Bot modela o próprio jitter dentro de `sigma` via `JITTER_RAD * dPrev`.
- Fora de alcance vira erro contínuo (`erroAlcance`), não veto binário.
- `|v_e|` em vez da componente perpendicular: conservador, sem `atan2`.

[Fonte: `docs/architecture-e2.md` §2.3]

### §2.4 — valor esperado

```
peso(e)    = 1 + PESO_FERIDO * (1 − e.hp / e.stat.maxHp)        // ∈ [1, 1+PESO_FERIDO]
VE(mira)   = Σ  pAcerto(e | mira) * peso(e)     sobre TODOS os inimigos vivos
```

O dano da habilidade **não** entra em `VE` — o bot não sabe quanto o Tremor machuca e não deve saber; isso é
o que faz o bot escolher *quando* e *onde*, não *qual* habilidade (cada bola só tem uma ativa, RF-03).

Conjunto de candidatos de mira: um por inimigo vivo (mirar na posição prevista daquele inimigo); no máximo 2
no 2v2. O bot escolhe o de maior `VE`.

`reposicao`/`utilidade` não têm `VE`; política declarada:

| `kind` | Política — a mesma para todo personagem |
|---|---|
| `reposicao` | Se `hp/maxHp < FUGA` → mira na direção **oposta** ao inimigo mais próximo. Senão, se o inimigo mais próximo está além do alcance do ataque básico → mira **nele**. Senão, não casta |
| `utilidade` | Casta se disponível e o inimigo mais próximo está dentro de `[minRange, maxRange]`, mirando nele |

[Fonte: `docs/architecture-e2.md` §2.4]

### §2.5 — limiar com decaimento

```
casta se  VE_melhor ≥ limiarEf(slot)

limiarEf(slot) = LIMIAR[slot] * max(PISO_LIMIAR, 1 − esperaMs / DECAIMENTO_MS)
   onde esperaMs = tempo desde que o slot ficou disponível
```

Sem o decaimento, um personagem cujo `VE` raramente cruza o limiar **nunca casta a ult**, e a matriz reporta
como fraqueza de personagem o que é timidez de bot. `PISO_LIMIAR` impede cast aleatório.

[Fonte: `docs/architecture-e2.md` §2.5]

### §2.6 — jitter e `PRESET_ARNES`

| # | Jitter | Onde entra | Imita |
|---|---|---|---|
| 1 | Ângulo | rotaciona `(dx,dy)` por `(r()*2−1) * JITTER_RAD` | mira imprecisa |
| 2 | Distância | `mag += (r()*2−1) * JITTER_MAG`, clampado em [0,1] | arrasto curto/longo demais |
| 3 | Reação | próximo instante de decisão: `tick + REACAO_TICKS + floor(r() * REACAO_JITTER_TICKS)` | tempo de reação humano |

```
LIMIAR.ability = 0.55   LIMIAR.ult = 0.80   PISO_LIMIAR = 0.35   DECAIMENTO_MS = 8000
PESO_FERIDO = 1.0       FUGA = 0.35         LAG_S = 0.08
JITTER_RAD = 0.12 rad (≈6,9°)   JITTER_MAG = 0.10
REACAO_TICKS = 9   REACAO_JITTER_TICKS = 7      → decide a cada 150–250 ms
```

Esses números são **política de bot, não balanceamento**. Trocá-los muda a matriz inteira — por isso o CLI
(`e2.5`) exige que nenhuma matriz seja reportada sem a versão do bot que a produziu.

[Fonte: `docs/architecture-e2.md` §2.6]

### §3 — o PRNG do bot (executa D-08/RF-46)

```
createBot(matchSeed, team) → rand = mulberry32(deriveSeed(matchSeed, team + 1))
//                                                              team 0 → stream 1
//                                                              team 1 → stream 2
```

O estado do gerador vive **no objeto do bot**, nunca em `World` — isso já foi construído por `debt.7`
(`deriveSeed`, tabela de streams reservados em `sim/rng.ts`); esta story é o primeiro consumidor real de
stream ≠ 0.

Ordem de saque (§3.2, contrato):
```
para cada bola viva minha, NA ORDEM DE view.balls:
    se view.tick < st.proximaDecisaoTick: continua
    (1) r() → agenda a próxima decisão                        ← sempre, mesmo sem castar
    avalia ult; se casta:  (2) r() → ângulo   (3) r() → mag
    avalia ativa; se casta: (4) r() → ângulo  (5) r() → mag
```

Mudar essa ordem muda a matriz sem mudar uma linha de política — por isso ela é contrato, e por isso
`BOT_VERSION` existe.

[Fonte: `docs/architecture-e2.md` §3.1, §3.2]

### Completion Notes

**1. ARCH-001 (`dash.speed`) — a decisão obrigatória desta story, e o raciocínio.**

O gate de `e2.2` mediu que `tImpacto = d / S.speed` (§2.3, a mesma linha para `raio` e para
`dash`) não significa a mesma coisa nos dois casos: o `raio` do Vex é projétil e tem **98,2%** de
fidelidade entre velocidade declarada e real; o `dash` do Golem é o próprio corpo e tem **61%**,
porque `physics.ts:18` aplica `v *= drag^dt` a cada tick. O gate foi explícito em que passar sem
decisão não é aceitável.

**Decidido: corrigir, e corrigir pela lei que o motor de fato roda.** Para `kind: 'dash'`, o
estimador usa a velocidade **média sobre a janela declarada**, integrando `v(t) = v0 · drag^t`:

```
v̄ = S.speed · (1 − drag^T) / (T · −ln drag)        T = S.ms/1000,  drag = self.stat.drag
```

Por que esta forma e não outra, em ordem de peso:

- **Não é constante calibrada.** Um fator `0.61` ajustado ao Golem seria um número por personagem
  disfarçado de fórmula genérica — exatamente a opção C que §2.2 rejeitou, entrando pela porta dos
  fundos. Um personagem novo da Fase 5 com `drag` diferente herdaria o viés do Golem.
- **Não lê nada novo.** `self.stat.drag` já está no `WorldView` e `S.ms` já está declarado em
  `AimSpec` — inclusive resolve metade de REQ-001 (o gate de `e2.2` registrou que `dash.ms` não
  tinha consumidor nenhum na política escrita; agora tem). `sim/` não muda uma linha.
- **É a mesma lei, não um modelo paralelo.** `drag^dt` por tick é `drag^t` no contínuo; a fórmula é
  a integral disso, não uma aproximação inventada.

**Viés residual, medido e registrado — não corrigido, de propósito.** A fórmula dá **77,2%** onde a
medição do gate deu **61,1%**. A diferença é a **IA de movimento** puxando a velocidade de volta
para `maxSpeed` (105 px/s contra os 900 do dash) durante a janela. Modelá-la é o que o bot **não
pode** fazer: movimento é autoral (RF-12) e mora no closure `move` do personagem — lê-lo seria
voltar ao problema código-versus-dado que `AimSpec` existe para resolver, e desta vez sem nem o
consolo de um campo declarado. O saldo, com números:

| | `tImpacto` a 280px | erro vs. real | fidelidade |
|---|---|---|---|
| `S.speed` cru (a letra de §2.3) | 0,311 s | **−38,9%** | 61,1% |
| corrigido (o que este bot faz) | 0,403 s | **−20,8%** | 77,2% |
| real medido | 0,509 s | — | 100% |

A assimetria de fidelidade entre Golem e Vex — que é o que ARCH-001 realmente denuncia, não o erro
em si — cai de **37 pp** (98,2% × 61,1%) para **21 pp** (98,2% × 77,2%). O erro remanescente é do
mesmo **sinal** para o dash (o bot acha que chega antes do que chega), então continua sendo
otimismo, e não passou a ser pessimismo. Fica como entrada para a métrica de utilização de kit de

**4. Generalização de `erroAlcance` para `erroMira`, registrada porque muda uma linha de §2.3.**
§2.3 escreve o último termo de `sigma` como `erroAlcance = |dPrev − alcanceEf|`, que só está
definido para o inimigo **em quem se mira**. Mas §2.4 soma `pAcerto` sobre **todos** os inimigos
vivos, inclusive os que não são o alvo — e para esses `erroAlcance` não quer dizer nada. O termo
implementado é `erroMira = dist(pontoDeImpacto, posiçãoPrevista(e))`, que **se reduz exatamente a
`|dPrev − alcanceEf|`** quando `e` é o alvo mirado (o ponto de impacto está sobre o raio até ele) e,
para os demais, mede o quanto a mira passou longe. Sem isso o somatório de §2.4 fica indefinido;
com isso §2.3 continua valendo palavra por palavra no caso que ela descreve. Não é desvio de
desenho — é a única leitura que faz as duas seções coexistirem.

### ARCH-001 — a decisão obrigatória: **CORRETA, sem objeção**

A matemática foi derivada do zero, não conferida. `physics.ts:18` roda `v *= Math.pow(drag, dt)` por
tick, e `drag^dt` composto *n* vezes é `drag^(n·dt)` — logo `v(t) = v0·drag^t` **exatamente**. A média
temporal em `[0,T]` é `v0·(1−drag^T)/(T·(−ln drag))`, linha por linha o que `velEfetivaDash` implementa.

| Caminho | Valor | Confere? |
|---|---|---|
| Analítico (golem, `drag 0.3`, `T=0.45`) | **694,85 px/s = 77,21%** | bate os 694,9 / 77,2% alegados |
| Integração discreta do laço EXATO de `physics.ts` (27 ticks) | 687,91 px/s = 76,4% | a integral fica 1,00% acima da soma de Riemann — o desvio de `dt/2`, irrelevante num heurístico |
| Medição REAL num mundo em execução, IA de movimento no laço | **543,22 px/s = 60,4%** | o gate de `e2.2` mediu 61,1% com outro setup — mesma ordem |

Ordenação testada como asserção: **real (543) < modelado (695) < declarado (900)**. A correção anda na
direção da realidade sem ultrapassá-la, e o resíduo continua sendo *otimismo* — o sinal do erro não
inverteu. `tImpacto` a 280px: cru 0,311s · corrigido 0,403s · real 0,515s; erro cai de −39,6% para −21,7%.

**Julgamento:** aprovo. Usa só dado já declarado (`S.ms`, `self.stat.drag`), não toca `sim/`, deriva da
lei que o motor de fato roda, e degrada para `S.speed` fora do domínio em vez de produzir `NaN`. Um fator
calibrado a 0,61 teria sido a opção C de §2.2 entrando pela porta dos fundos, e envenenaria qualquer
personagem futuro com `drag` diferente. O @dev nomeou esse risco antes de mim e escolheu certo. Bônus:
resolve metade de REQ-001 — `dash.ms` ganhou consumidor. **ARCH-001 está encerrado.**

### Lâmina Fantasma — o achado do @dev: número **confirmado**, conclusão **ampla demais**

Recomputado analiticamente e reproduzido no bot. Lâmina tem `minRange = maxRange = 200` e `aim.radius = 9`.
Contra outro Vex (`radius 15`), `raioEf = 24`; no melhor caso possível dois dos três termos de `sigma`
zeram e sobra `JITTER_RAD·dPrev = 0,12·200 = 24`. Logo `pAcerto = 24²/(24²+24²) = **0,5 exato**`. Contra
Golem (`raioEf = 33`): 0,6541. Confirmado no bot real: 1v1 vex-vs-vex com alvo cheio a d=200 → não casta.

Mas a Completion Note 5 diz que `LIMIAR.ability = 0,55` é "**inalcançável**", e isso confunde `pAcerto`
com `VE`. §2.4 define `VE = Σ pAcerto·peso`, com `peso ∈ [1,2]`. Medi a fronteira: alvo a 95% de hp → VE
0,525, espera; alvo a **90%** de hp → VE 0,550, **casta**. Em 2v2 o somatório destrava antes ainda. O
próprio dado do @dev confirma — o Vex castou 2×, não zero.

A formulação correta é *mais* interessante para `e2.5`: não é **kit morto**, é **kit adiado** — no espelho
Vex a Lâmina fica estruturalmente indisponível enquanto ninguém está ferido, acoplando o uso do kit ao
progresso da luta. Viés de competência emergindo sem nenhum ramo por personagem, exatamente como §8.3
prevê. **Achado de `e2.5`, não defeito desta story** — §2.6 proíbe mexer no preset sem dado, e o @dev
acertou em não mexer.
