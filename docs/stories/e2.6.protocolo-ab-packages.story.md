## Story

**Como** desenvolvedor executando o passo 6 do plano de construção da Fase 2 (`docs/architecture-e2.md`
§7) — o passo onde os dois critérios centrais do portão da Fase 2 (P2.2, P2.3) viram comando executável,
**eu quero** criar `src/tools/packages.ts` com pacotes de item nomeados (`fisico`, `dano`, `nenhum`), e
acrescentar ao CLI as flags `--pacote`/`--alvo` (protocolo A/B com linha-base espelhada) e `--mutacao`
(mutação arbitrária por campo),
**para que** o teste de mutante (P2.2) e o controle negativo (P2.3) sejam executáveis por comando, sem que
o CLI aceite campo cru na linha de comando para os pacotes de risco — o que evitaria a armadilha de sinal
já detectada na arquitetura (a leitura literal do PRD para o pacote físico **inverte o sinal esperado**).

## Acceptance Criteria

**`packages.ts` — pacotes nomeados, não campo cru (§5.2):**

1. `src/tools/packages.ts` (novo) — dado, sem lógica — exporta:
   ```ts
   export const PACOTES = {
     fisico: { mass: +0.20, drag: +0.20 },  // Chumbo +massa · Lixa −atrito = +drag (retenção)
     dano:   { dmg:  +0.20 },               // Lâmina +dano
     nenhum: {},                            // controle negativo (P2.3)
   }
   ```
   (`docs/architecture-e2.md` §5.2, literal — note que `drag: +0.20` para o pacote físico é a leitura
   **correta**: Lixa é `−atrito`, e `drag` é a fração de velocidade **retida**, então "menos atrito" é
   `drag` **positivo**, não negativo — a leitura literal do PRD, `drag: −0.20`, inverteria o sinal e mediria
   o oposto do pretendido).
2. O CLI **nunca** aceita campo cru na linha de comando para os pacotes de risco — só nomes definidos em
   `packages.ts` (`--pacote=nenhum|fisico|dano`). Mutação arbitrária por campo continua existindo,
   separadamente, via `--mutacao=vex:dmg:+0.30`, para P2.2 — onde o campo **é** o que se quer nomear
   (`docs/architecture-e2.md` §5.2).

**Protocolo A/B com linha-base espelhada (§5.3):**

3. Para uma composição `C` (a mesma dos dois lados) e um pacote `P` aplicado a **um** personagem de **um**
   lado: seeds `1..n/2` → pacote no time 0; seeds `n/2+1..n` → pacote no time 1; `winrate medido =
   vitórias do lado modificado / rodadas decididas`.
4. O protocolo isola a mutação (tudo o mais idêntico dos dois lados: mesma composição, build, bot,
   política), cancela o viés de lado pela troca (herdada de `e2.5`), e **não depende de o roster estar
   balanceado** (`docs/architecture-e2.md` §5.3 — a leitura alternativa de P2.3, "a matriz de composições
   permanece dentro de 45–55%", é insatisfazível por construção: é o próprio portão da Fase 5).
5. Flags `--pacote=nenhum|fisico|dano` e `--alvo=vex` (a qual personagem do lado modificado o pacote se
   aplica) implementam o protocolo A/B (`docs/architecture-e2.md` §6.2).
6. A aplicação do pacote usa o mecanismo de `PickSetup.itemBonus` já existente desde `e2.1` — nenhum
   caminho de código exclusivo de teste é criado.

**Aviso de clamp (§5.1, corolário):**

7. Se um pacote pedido (via `--pacote` ou `--mutacao`) for cortado pelo teto de balanceamento (`ΣMAX`) já
   existente em `recomputeStats`, o CLI **avisa** explicitamente — um `+150%` de `dmg` silenciosamente
   reduzido para `+100%` não pode ser interpretado como falha do arnês (`docs/architecture-e2.md` §5.1:
   "um teste de mutante negativo seria interpretado como falha do arnês, quando foi o clamp funcionando").

**P2.2 e P2.3 executáveis pelo CLI (§9/R-02, Anexo B):**

8. `npm run balance -- --mutacao=vex:dmg:+0.30` reporta o confronto correspondente **fora** de 45–55%

**Saída (§6.3):**

## Dev Notes

### A armadilha do sinal — por que `packages.ts` existe (fonte: `docs/architecture-e2.md` §5.2, literal)

> O Risco #1b está escrito no PRD como "pacote físico (**+20% massa, −20% drag**)". Traduzido literalmente
> para campos, `drag: −0.20` significa **mais atrito**, porque `drag` é a fração de velocidade *retida* por
> segundo (`architecture.md` §1.6, R-01). Os itens pretendidos são Chumbo (+massa) e Lixa (−atrito), e Lixa
> é **`drag: +0.20`**.
>
> Não é preciosismo. Medido (§5.4, n=800 cada):
>
> | Pacote aplicado ao Vex | Δ winrate vs linha-base |
> |---|---|
> | `{ mass: +0.20, drag: +0.20 }` — a **intenção** (Chumbo + Lixa) | **+4,32pp** |
> | `{ mass: +0.20, drag: −0.20 }` — a **letra** do PRD | **−5,90pp** |
>
> Dez pontos percentuais de diferença, com troca de sinal. [...] Um erro de sinal de uma linha reprojetaria
> a Fase 3.
>
> **Decisão de arquitetura:** o CLI nunca aceita campo cru na linha de comando para os pacotes de risco. Ele
> aceita **nomes de pacote**, definidos uma única vez em `src/tools/packages.ts`, com o nome do item ao lado
> do campo e do sinal:
> ```ts
> export const PACOTES = {
>   fisico: { mass: +0.20, drag: +0.20 },  // Chumbo +massa · Lixa −atrito = +drag (retenção)
>   dano:   { dmg:  +0.20 },               // Lâmina +dano
>   nenhum: {},                            // controle negativo (P2.3)
> }
> ```
> Mutação arbitrária por campo (`--mutacao vex:dmg:+0.30`) continua existindo para P2.2, onde o campo é o
> que se quer nomear.

[Fonte: `docs/architecture-e2.md` §5.2]

### O protocolo A/B, literal (fonte: §5.3)

```
composição C (a mesma dos dois lados)   ·   pacote P aplicado a UM personagem de UM lado
seeds  1 .. n/2   → pacote no time 0
seeds n/2+1 .. n  → pacote no time 1
winrate medido = vitórias do LADO MODIFICADO / rodadas decididas
```

> Três propriedades, e as três são necessárias: (1) isola a mutação — tudo o mais idêntico dos dois lados;
> (2) cancela o viés de lado pela troca; (3) não depende de o roster estar balanceado — a leitura
> alternativa de P2.3 ("a matriz de composições permanece dentro de 45–55% sem mutação") é insatisfazível
> por construção — isso *é* o portão da Fase 5.

[Fonte: `docs/architecture-e2.md` §5.3]
